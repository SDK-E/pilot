## Pilot

Read `docs/progress.md`, `docs/decisions/0001-platform-boundaries.md`, and `docs/decisions/0004-mastra-conversation-runtime-contract.md` before continuing. Keep them synchronized with verified implementation and environment changes.

- WorkOS is the required auth provider. Use application-specific credentials. Authenticate and authorize every server mutation; never trust a submitted organization ID or model decision as authorization. When a Route Handler calls `withAuth()`, its path must be included in `src/proxy.ts`'s AuthKit matcher; add a regression test for its anonymous and forged-session boundary.
- Use current official documentation and inspect installed types/source before choosing APIs. Prefer maintained packages, Mastra runtime capabilities and official shadcn components over custom infrastructure.
- Keep product/domain logic in Pilot, Mastra implementation in `pilot-ai`, integration adapters in `pilot-integrations`, and shared design-system sources in `pilot-ui`.
- Keep local, preview and production secrets separate. Never log or commit credentials. Do not expose worker capabilities until system-enforced permissions and approval behavior exist.
- Production schema migrations run from the Vercel production build using `DATABASE_URL`; do not try to pull a sensitive production URL locally. Keep the build migration conditional on `VERCEL_ENV=production` so previews never migrate production data.
- Conversations are Pilot-owned, creator-scoped sessions within an organization. Their message records and protected runtime client must remain server-only. Filter every chat, message, stream, deletion, and activity query by `createdByWorkosUserId` unless an explicit, separately authorized sharing model is implemented. Do not enable message submission for an environment until its Turso-backed Mastra runtime and authenticated transport are configured and verified; do not expose tools.
- Projects are Pilot-owned, creator-scoped collections. Project instructions and explicitly enabled shared memory may reach Pilot AI only through its server-verified project command, after exact owner, organization, and conversation membership checks. Never use a project to bypass private-chat ownership. Project files, knowledge, sharing, and cross-user memory remain disabled until each has explicit storage, retrieval, deletion, and authorization behavior.
- Before a private conversation leaves a project with shared memory, clear that project's runtime resource while the existing association remains authorized. Do not move or remove the database association if that cleanup fails: resource-scoped observations must never remain available through a former project.
- Organization preferences are Pilot-owned configuration. Every update must authenticate the WorkOS caller, recheck active membership, and scope a referenced agent to the active organization. Preferences must fail safe when a referenced capability is deleted or unavailable.
- The chat interface may show only capabilities backed by the protected runtime contract. Research may be enabled only when `PILOT_RESEARCH_ENABLED=true`, the matching runtime is enabled, and the OIDC-authenticated activity callback is configured. Do not add attachment, browser, scratchpad, MCP, write, or approval controls until their events, persistence and authorization behavior exist.
- Until a durable approval suspension and decision flow is implemented, a Research tool may run only when its persisted rule is explicitly `allow`; `ask`, `deny`, and `auto-classifier` are fail-closed and must not invoke a tool.
- Execution and activity records are Pilot-owned and organization-scoped. Record lifecycle events from verified server work only; never persist reasoning, tool secrets, tool payloads, URLs, errors, or browser-supplied activity as an audit event. Tool events may persist only a known capability ID, call ID, and server-generated status summary.
- A model ID is configuration input, not authority to select a provider. Development uses allowlisted Kilo Gateway model `kilo/kilo-auto/free`; do not make a generation until its environment-specific configuration and authenticated Pilot-to-runtime transport are configured and tested.
- Run `pnpm check`, `pnpm build`, `pnpm test`, `pnpm test:server`, `pnpm test:db`, and `pnpm audit --audit-level high` for a completed persistence slice. Browser tests require a fresh build; `test:server` verifies Pilot's protected runtime stream parser; `test:db` uses the isolated development Neon database and removes its randomized fixtures. A green build is not evidence of successful authentication or durable execution.
- No `getSignInUrl()` or cookie-writing helpers during Server Component rendering. Use proxy, Route Handlers or Server Actions. Sign-out is a POST Server Action.
- Complete one worker end-to-end before adding broad secondary features. Keep unimplemented behavior explicit in documentation.
- A Research `ask` rule is a durable Mastra tool-call suspension, not a UI convention. Persist and resume only the server-derived run ID and tool-call ID; approval records and activity events must never contain a query, URL, tool input/output, error, prompt, or reasoning. An approval decision must recheck WorkOS membership and private conversation ownership, atomically claim the pending record, then have Pilot AI verify the exact suspended Research run before acting. Do not retry an uncertain resume.
- For a Research tool rule of `ask`, use Mastra's persisted `requireToolApproval` and `approveToolCall`/`declineToolCall` APIs. Recreate the request-scoped agent with a public Mastra registration over the same Turso storage when resuming, then verify the stored run's conversation resource, tool name, and tool-call ID before action. Keep the callback payload limited to the fixed capability ID, lifecycle state, organization ID, execution ID, runtime run ID, and tool-call ID.
- Organization-wide task and approval indexes must preserve private-chat ownership: standalone tasks filter by their creator, and conversation tasks or approvals join through `conversations.createdByWorkosUserId`. Membership alone is never sufficient to read another member's task or approval metadata.
- Agent visibility and default-agent selection must use the same environment capability check as conversation preparation. Do not render or persist a disabled Research agent as a selectable default and defer failure until the first message.
- Persona goals, tone, and output format are behavioral configuration. Build them with the shared server-only persona instruction helper at every runtime boundary (new chat, follow-up stream, and approval resume); do not accept an instruction packet from the browser or leave stored persona settings display-only.
- The bounded `web-search` capability is available to Conversational and Research personas only when their saved rule is `allow` or `ask`. Use the same server-derived tool authorization, OIDC callback, persisted Mastra suspension, and private-chat approval checks for both agent bases. Do not expose another tool until it has equivalent authorization, activity, storage, and approval behavior.
- Keep persona tool controls derived from the shared capability catalog. A planned capability must render as unavailable and cannot become an enabled runtime tool merely because a persisted preference exists.
- Private chat attachments belong to a creator-scoped conversation. Store only server-derived metadata in Neon, keep file bytes in private Blob, and stream reads only after WorkOS, organization, worker, conversation, and creator checks. Never treat a Blob URL from the browser as authorization or send a file to Pilot AI without a dedicated ingestion/deletion contract.
- Attachment text extraction must reload only owned attachment metadata and private Blob bytes on Pilot's server immediately before generation. Keep extraction to explicitly supported formats, bound excerpts, label them untrusted, and append them only to the server-built runtime instructions; never transmit Blob URLs, browser metadata, or attachment content through activity or approval records.
- Persona duplication must reload the organization-scoped source configuration on the server after WorkOS membership verification. Copy configuration only; never copy conversations, runtime memory, tasks, approvals, executions, or activity.
